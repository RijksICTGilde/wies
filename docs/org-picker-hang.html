Performance regression · post-mortem

The opdrachtgever-picker hangs the browser on open

With a production-scale org list (~3–4k organisations), opening the “Opdrachtgevers selecteren” modal freezes the tab for several seconds. The browser blames a plugin — that is a misattribution.

Where assignment-create form → “Opdrachtgever toevoegen” Since NLDD design-system migration Layer client-side JS
Root cause

The org tree is built entirely client-side, eagerly and recursively on modal open. Every branch — even collapsed ones — is fully materialised, and each node is now 5–9 NLDD Lit web components instead of native HTML. That is ~20–40k custom-element upgrades running synchronously in one pass. The node count didn’t change; the cost per node did.

01 How the modal renders

The template ships an empty container plus the whole hierarchy as a JSON blob, then hands rendering to JavaScript:

assignment_org_modal.html → empty <div> + json_script (whole tree)
→ assignment_org_tree.js builds TreeState (cheap, in-memory) + tree.render()
→ org_tree.js render() → _buildRow() recurses into every child

In org_tree.js, _buildRow(node, depth) recurses into node.children regardless of expansion. Collapsed branches are hidden only by omitting an expanded attribute — the full DOM subtree is created anyway. Then sync() walks the whole tree a second time.

Per node it creates nldd-list-item, one nldd-spacer-cell per depth level, a chevron (nldd-list-item-action + nldd-icon-cell + nldd-icon), and the row (nldd-list-item-action + nldd-cell + nldd-checkbox + nldd-spacer-cell + nldd-text-cell). Each is a Lit element that upgrades and first-renders on creation.

02 Why it’s a regression — and where it comes from

The old renderer on main (org_tree_base.js, pre-NLDD) built the tree just as eagerly and recursively — identical node count. The difference is entirely what each node is:

main · pre-NLDD

“Not super snappy” (large DOM) but no hang.

<li> <button> <span>
<label> <input type=checkbox>
— native, nearly free to create

NLDD branch · now

Same tree, but each node is a stack of Lit web components.

nldd-list-item
nldd-spacer-cell × depth
nldd-checkbox, nldd-text-cell …
— each upgrades + first-renders

So it comes from the introduction of web components, via the shared renderer org_tree.js — not a JS-logic change, not the node count, and not a stray plugin. Same eager full-tree build × a far more expensive per-node upgrade = a synchronous multi-second freeze.

03 Ruled out

  • The JSON payload. The picker ships all orgs unpruned (count_mode=none → prune_empty=False), but ~3–4k nodes as data parse once and are cheap. The hang is DOM materialisation, not parsing.
  • TreeState. The in-memory index + cascade is pure and O(n) with no DOM. Fine as-is.
  • The “plugin” warning. The browser’s resource warning misattributes the main-thread block; it originates in the app’s own synchronous element construction.
  • NLDD offering a lazy tree. Checked the source: nldd-list-item renders children via <slot name="children"> and only toggles hidden on collapse — the slotted DOM must already exist. No built-in lazy rendering to lean on.

04 Fix direction (not in scope — for a follow-up)

Investigation only was requested; recorded here for whoever picks up the fix.

Recommended · lazy child rendering

Build only the root groups and their immediate children on open. Build a branch’s deeper descendants only when it is first expanded (chevron, keyboard, expandAncestorsOf for restored selections, and on-demand during search). Initial upgrades drop from ~20–40k to a few hundred.

Safe with NLDD: nldd-list-item reacts to slotchange and derives ARIA (aria-level/-posinset/-setsize) from live nesting, so appending child rows after render stays correct. TreeState already holds the full model, so search and cascade keep working over the whole tree.

Lives entirely in the shared org_tree.js, so the opdrachtgever filter sheet (client_tree.js) benefits for free. Decided detail: search should ignore queries under 2 characters, or a 1-char substring match would force-build most of the tree and re-introduce the hang.

Alternatives rejected: chunked/async building (only defers the same total work), virtualization (large rewrite; breaks keyboard/search/a11y assumptions), fewer elements per node (helps but still eager). No server change needed.

Reproduce: just load-full-data (~3–4k orgs) → “Opdracht invoeren” → “Opdrachtgever toevoegen”. A DevTools Performance profile of the open shows a multi-second synchronous block dominated by custom-element upgrades / Lit first-render. Confirmed by diffing org_tree.js against ccfa5d04^:org_tree_base.js and reading the NLDD list-item source.
